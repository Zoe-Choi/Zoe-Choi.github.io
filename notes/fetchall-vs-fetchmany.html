fetchall vs fetchmany (execute)

정리 2026-06-25

한 줄 정의

execute는 쿼리를 DB에서 실행만 시키고, 결과 행을 파이썬으로 가져오는 건 fetch 단계다. fetchall은 전체를 한 번에, fetchmany는 청크 단위로 가져온다.

자세히

  • execute(sql): 쿼리를 DB 서버에 보내 실행. 결과 집합은 서버(또는 드라이버 버퍼)에 준비됨. 이 단계는 행을 파이썬 메모리로 끌어오지 않음 -> 5천만 건이어도 execute 자체는 통과.
  • fetchall(): 결과 전체를 한 번에 파이썬 리스트로 적재. 5천만 행이면 전부 메모리에 올리려다 MemoryError/OOM, 또는 전송이 오래 걸려 쿼리 유휴 -> Trino query.client.timeout 으로 abort. (execute는 되는데 fetchall에서 터지는 이유)
  • fetchmany(size): size개씩 끊어서 가져옴. 루프 돌며 청크 처리 -> 메모리는 청크 하나 크기로 일정.
  • fetchone(): 한 행씩. 메모리는 최소지만 호출 왕복이 많아 느림.
  • cursor: 결과를 가리키는 포인터. fetch는 그 포인터를 앞으로 옮기며 행을 가져오는 동작.

왜 중요한가 / 어디서 쓰나

  • 대용량 SELECT를 파이썬으로 처리/시각화할 때 fetchall은 위험. fetchmany 루프나 server-side cursor, pandas read_sql(chunksize=...)로 스트리밍.
  • 진짜 해법은 보통 "DB에서 줄여서 가져오기": GROUP BY 집계, 샘플링, LIMIT, 기간 필터. 시각화에 5천만 원시 점은 의미도 없음(다운샘플/집계 후 가져와야).
  • Trino: query.client.timeout(기본 5m) = 클라이언트가 결과를 안 가져가면 쿼리 취소. fetchall로 오래 끌면 이 타임아웃에도 걸림.

예시 / 코드

cur.execute(sql)            # 실행만 (행 전송 X)

# 나쁨: 전체를 메모리에
rows = cur.fetchall()       # 5천만 건 -> 메모리/타임아웃으로 터짐

# 좋음: 청크 스트리밍
while True:
    rows = cur.fetchmany(10000)
    if not rows:
        break
    process(rows)

# pandas 청크
for chunk in pd.read_sql(sql, conn, chunksize=100000):
    handle(chunk)

# 가장 좋음: DB에서 집계해 작게 가져오기
# SELECT dt, region, COUNT(*) FROM t GROUP BY dt, region

관련 개념

  • Trino query.client.timeout
  • server-side cursor / streaming
  • 다운샘플링 / 집계 쿼리
