커밋 SHA 검증

정리 2026-07-30

한 줄 정의

git push 종료 코드를 믿지 않고, push 후 원격에 다시 물어서 "그 브랜치가 내가 밀어넣은 커밋을 정확히 가리키는지" 대조하는 배포 승격 단계의 안전장치.

자세히

LOCAL="$(git rev-parse HEAD)"                             # 내가 체크아웃한 커밋
REMOTE="$(git ls-remote prod refs/heads/main | cut -f1)"   # 원격 main이 실제 가리키는 커밋
[ "$LOCAL" = "$REMOTE" ] || { echo "sha 불일치"; exit 1; }
  • git ls-remote는 clone 없이 원격의 ref -> sha 매핑만 읽어오므로 비용이 거의 없다
  • push 실패 대부분(non-fast-forward, 권한, pre-receive 훅 거부, 네트워크)은 이미 종료 코드로 잡히고 GitHub Actions run:은 기본 bash -e라 거기서 멈춘다. 따라서 이 검증이 추가로 잡는 범위는 좁다
    • 경쟁 갱신: push 직후 다른 주체가 같은 브랜치를 또 갱신한 경우
    • 서버 측 변형: 미러/게이트웨이 구성에서 ref가 다른 커밋으로 바뀌는 경우
    • 이후 배포 단계가 이 sha를 전제로 도는데 그 전제가 틀렸는지를 배포 전에 끊음
  • 못 잡는 것: remote URL 오타로 엉뚱한 저장소에 push하면 ls-remote도 같은 곳을 보므로 두 값이 일치한다. remote URL을 secret/variable로 고정해 막을 문제
  • 실질 가치는 실패 탐지보다 증적에 있다. 실행 로그에 "이 시각 원격 main = 이 sha"가 남는다

왜 중요/어디서 씀

망분리 환경에서 개발 git -> 운영 git 승격을 자동화할 때 쓴다. 관련: Actions CD 파이프라인 설계

수작업은 왜 안 하나: 안 하는 게 아니라 사람이 push 후 운영 git 화면을 눈으로 확인하고 있고, 검증이 사람 머릿속에만 있다. 그래서 확인했다는 증거가 없고, 건너뛰어도 모르고, 잘못 봐도 탐지되지 않는다. 자동화하면 화면을 보던 사람이 사라지므로 그 눈을 명시적 assert로 옮겨야 하고, 그 과정에서 증적 문제도 같이 해결된다.

이 검증 + 사람의 운영 git 직접 push 차단이 둘 다 성립해야 "운영에 있는 코드 = 개발 git에서 리뷰·승인된 그 코드"가 증명된다. 금융권 변경관리 감사에서 요구되는 지점.

전제: 승격 방식이 sha를 보존해야 한다. clone 후 push면 유지되지만, 파일 복사 후 운영 git에서 재커밋하는 방식이면 두 저장소 히스토리가 별개라 비교 대상 자체가 없다.

예시

헷갈리기 쉬운 다른 의미의 "SHA 고정"은 완전히 다른 주제다. 서드파티 action의 태그는 소유자가 다른 커밋으로 옮길 수 있어서, 공급망 공격 방어를 위해 커밋 SHA로 핀 고정하는 관행이다.

- uses: actions/checkout@v4                                          # 태그. 내용이 바뀔 수 있음
- uses: actions/checkout@8f4b7f84864484a7bf31766abe9204da3cbe65b3    # SHA 고정. 불변
