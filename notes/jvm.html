JVM

정리 2026-09-02

한 줄 정의

Java Virtual Machine. Java, Scala, Kotlin 소스를 컴파일한 바이트코드(.class, .jar)를 OS/CPU 종류와 무관하게 실행해 주는 런타임.

자세히

소스 -> 바이트코드 -> JVM 실행 구조다. 컴파일 결과가 기계어가 아니라 바이트코드이므로 같은 jar를 Linux, Windows 어디서든 돌린다.

운영에서 드러나는 JVM 특성:

  • 프로세스 시작 시 힙을 미리 확보하고 GC가 회수한다. 그래서 -Xmx, -Xms, GC 옵션 튜닝이 필수 작업이 된다.
  • JIT 컴파일러가 자주 실행되는 코드만 네이티브로 변환한다. 기동 직후는 느리고 워밍업 후 빨라진다.
  • 설정이 파일로 남는다. Trino jvm.config, Hadoop hadoop-env.sh의 HADOOP_HEAPSIZE, Spark spark-defaults.conf의 executor memory 등.

JVM은 "웹이냐 아니냐"의 반대말이 아니다. 축이 다르다.

  • 런타임 축: 무엇으로 실행되는가. JVM, Node.js, CPython, .NET CLR, PHP-FPM.
  • 역할 축: 무슨 일을 하는가. 웹 서비스, API, 배치, 쿼리 엔진, 메시지 브로커.

Spring Boot는 JVM 웹 앱이고, Trino는 JVM 쿼리 엔진이다. 런타임이 같아도 역할이 다르다.

왜 중요/어디서 씀

Hadoop, Hive Metastore, Spark, Trino, Nessie, Elasticsearch, Kafka가 모두 JVM 데몬이다. PySpark를 써도 실제 처리는 JVM executor가 한다.

파일 무결성 모니터링(FIM) 경로 설계에서 이 구분이 실무적으로 갈린다.

  • 웹 스택: document root 변조(웹셸 삽입)가 핵심 위험. /var/www/html, .php, SSR 빌드 산출물을 감시한다.
  • JVM 데이터 플랫폼: document root가 없다. 실행 코드가 jar이므로 jar 디렉터리 교체가 곧 임의 코드 실행이다. $SPARK_HOME/jars, /usr/lib/trino/plugin, $HIVE_HOME/lib이 웹의 document root에 대응하는 감시 지점이다.
  • 여기에 설정 파일(접속정보, 권한 정책)과 인증 자료(keytab, keystore)를 더한다. 데이터/로그/셔플 디렉터리는 변경 빈도 때문에 제외한다.

WAS와의 차이

전통적 WAS는 Tomcat, WebLogic, JEUS 같은 애플리케이션 서버 제품을 따로 설치하고 WAR/EAR를 webapps/나 deployments/에 배포하는 구조다. JVM 데이터 플랫폼은 각 컴포넌트가 Jetty 같은 HTTP 서버를 자기 프로세스 안에 내장(embedded)한다. 별도 WAS 제품도, WAR 배포 디렉터리도 없다.

내장 서버 기본 포트(설치마다 다름):

  • Hadoop: NameNode 9870, DataNode 9864, ResourceManager 8088, JobHistory 19888
  • Spark: 잡별 UI 4040, History Server 18080
  • Trino: coordinator 8080 또는 8443
  • Hive: Metastore는 Thrift 9083(HTTP 아님), HiveServer2 Web UI 10002
  • Nessie: REST 19120 (Quarkus 내장)
  • OpenMetadata: 8585 (Dropwizard 내장 Jetty가 React UI까지 서빙)

FIM 함의: WAS 표준 감시 경로(webapps/, server.xml, web.xml, 압축 해제된 WAR)가 존재하지 않는다. UI 정적 리소스는 jar 내부에 패키징되므로 jar 무결성 감시로 커버된다.
