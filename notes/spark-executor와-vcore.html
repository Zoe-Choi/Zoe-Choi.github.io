Spark executor와 vcore

정리 2026-09-14

한 줄 정의

executor는 Spark가 일을 시키는 작업반 하나이고, vcore는 그 반에 배정된 일손 수, num_executors는 반을 몇 개 만들지다. 총 처리 능력 = 반 개수 x 반당 일손.

자세히

공장 비유로 보면 이렇다.

용어비유실제
워커 노드공장 건물 한 동물리 서버
YARN공장 관리실자원을 나눠주는 스케줄러
Spark 앱(job)주문 하나테이블 하나 적재
executor작업반 하나메모리와 코어를 묶어 받는 실행 단위, JVM 프로세스
executor cores (vcore)반에 있는 일손 수그 반이 동시에 처리할 수 있는 task 개수
num_executors반을 몇 개 만들지앱이 요청하는 executor 개수
executor memory반이 쓸 작업대 크기executor 하나의 JVM 힙

계산은 단순하다.

주문 하나가 요구하는 일손 = num_executors x executor_cores
주문 하나가 요구하는 공간 = num_executors x executor_memory

vcore는 진짜 CPU 코어가 아니다

YARN의 vcore는 스케줄링 회계 단위다. cgroups CPU 제한을 켜지 않으면 실제 CPU를 묶어두지 않는다. 물리 코어보다 많이 배정(오버커밋)해도 컨테이너가 죽지 않고 각자 조금씩 느려질 뿐이다.

메모리는 반대다. 물리적으로 없으면 컨테이너가 죽는다. 그래서 메모리는 보수적으로, vcore는 관대하게 잡는 것이 일반적이다.

고정 요청의 문제

num_executors를 고정하면 큰 작업과 작은 작업에 같은 값이 적용된다. 작은 테이블이 필요량의 수백 배를 요청해 다른 앱의 자원을 뺏는다.

해법이 dynamic allocation이다. 적은 수로 시작해 task가 밀리면 자동으로 executor를 늘린다. --num-executors를 같이 넘기면 그 값이 초기 executor 수가 된다.

Using initial executors = 4, max of initialExecutors, minExecutors and spark.executor.instances
Requesting 1 new executor because tasks are backlogged (new desired total will be 5)

증가는 배수로 일어난다. 4 -> 5 -> 7 -> 11 -> 19 -> 35 식이고 라운드 간격이 약 1초라 수 초 안에 필요한 규모에 도달한다.

처음 값은 어떻게 정하나

순서가 있다. 코어 -> 메모리 -> 개수.

1. executor_cores: 2~5, 기본 4

  • 너무 적으면(1~2) 반이 많아져 JVM 기동 비용이 늘고 공통 데이터가 반마다 복제된다
  • 너무 많으면(6 이상) 한 executor 안에서 HDFS 동시 읽기가 서로 방해해 처리량이 떨어진다

2. executor_memory: 태스크 하나가 다루는 데이터에서 역산

파티션 하나 = 128~200MB
동시 처리    = executor_cores개
필요 공간    = cores x 200MB

힙 전부를 데이터에 쓰지 않는다. spark.memory.fraction 기본 0.6이라 실제 데이터용은 60% 수준이고 정렬/조인 중간 공간도 필요하다. 여유를 두면 4~8GB가 기본. 32GB를 넘기면 GC 정지가 길어져 역효과다.

3. num_executors: 데이터 크기에서

파티션 수      = 데이터 크기 / 150MB
필요한 총 코어 = 파티션 수 / 3
num_executors  = 총 코어 / executor_cores

100GB면 파티션 670개, 코어 220개, 4코어 executor 55개.

4. 한도 확인

컨테이너 크기(executor_memory + memoryOverhead)가 yarn.scheduler.maximum-allocation-mb를 넘으면 영원히 배정되지 않는다. 반대로 그 값이 yarn.nodemanager.resource.memory-mb보다 크면 그것도 모순이다.

5. 공식은 시작점일 뿐

돌린 뒤 실측으로 고친다.

관측해석조치
요청보다 훨씬 적게 사용과할당줄이기
executor를 늘려도 시간이 안 줄어듦이미 충분그만 늘리기
GC 시간이 김메모리 과다 또는 파티션 과대파티션 늘리기
컨테이너가 YARN에 killed여유분 부족memoryOverhead 상향

6. 크기 편차가 크면 공식이 무의미하다

같은 프로파일을 쓰는 작업의 실측이 수백 배 차이나면 고정값으로는 한쪽이 굶거나 낭비한다. dynamic allocation이 이 문제를 위해 존재한다.

왜 중요/어디서 씀

병목이 메모리인지 CPU인지에 따라 처방이 정반대다.

증상병목처방
앱이 큐에서 대기, 같은 작업이 실행마다 편차 큼메모리yarn.nodemanager.resource.memory-mb 상향
앱이 동시에 돌지만 각자 느림, 워커 CPU 80%+CPUexecutor 과요청 줄이기, dynamic allocation
컨테이너가 YARN에 killed힙 밖 메모리memoryOverhead 상향
executor에서 Java heap space파티션당 데이터 과다shuffle.partitions 상향

메모리 병목을 풀면 CPU가 다음 병목으로 드러나는 일이 흔하다. 병목이 사라지는 게 아니라 한 단계 뒤로 밀리는 것이다.

예시

2026-09 운영 하둡 클러스터 사례. 상세는 Hadoop 메모리 재설계.

워커 3대, 각 물리 메모리 252GB, logical core 32개 (총 96개)

튜닝 전
  YARN이 인식한 메모리  : 노드당 48GB, 합계 144GB   <- 증설분 미반영
  앱 하나의 요청        : executor 30개 x 4코어 = 일손 120명
                          executor 30개 x 4GB   = 공간 132GB
  결과                  : 주문 하나가 공장 전체를 요구. 나머지는 대기

조치 1 (메모리)
  노드당 48GB -> 160GB, 합계 480GB
  결과: 대기 해소. 최대 앱이 69,915 -> 153,130 MB로 2.2배 확보

조치 2 (CPU)
  num_executors 30 -> 4 + dynamic allocation
  결과: 작은 테이블은 4개로 끝, 큰 테이블은 자동 증설

조치 1 이후 워커 CPU가 84%, 81%로 올라간 것이 병목 이동의 신호였다. 앱들이 동시에 돌기 시작했다는 뜻이다.
