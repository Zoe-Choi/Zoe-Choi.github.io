정리 2026-06-29

1. Parquet 파일 구조와 Spark 읽기 원리

Parquet는 무엇인가

  • 행 중심이 아니라 컬럼 중심으로 저장하는 파일 포맷
  • 필요한 컬럼만 읽기 쉬워서 분석 쿼리에 유리
  • 압축 효율이 좋고, 컬럼 통계를 같이 저장해서 건너뛰기 최적화가 가능

구조

  • file
    • row group
      • column chunk
        • page
          • 실제 데이터와 인코딩 정보
  • footer에 schema, row group 위치, 통계 정보가 들어감

왜 빠른가

  • 필요한 컬럼만 읽음
  • row group 단위로 스킵 가능
  • min/max 통계로 불필요한 데이터 블록을 건너뜀
  • 압축과 벡터화 읽기와 잘 맞음

Spark가 읽는 과정

  1. 파일 목록을 찾음
  2. footer를 읽어서 schema와 row group 위치를 확인
  3. 필요한 컬럼만 남김
  4. filter pushdown이 가능하면 row group을 스킵
  5. 컬럼 chunk를 batch 단위로 읽음
  6. 디코딩해서 DataFrame으로 만듦

읽기 성능을 볼 때 보는 값

  • scanned bytes
  • scanned files
  • skipped row groups
  • 같은 쿼리의 실행 시간 변화

2. Spark와 Trino 차이

핵심 차이

  • Spark는 대용량 변환과 적재에 강한 배치 처리 엔진
  • Trino는 여러 저장소를 바로 읽는 분산 SQL 질의 엔진

Spark가 대용량 ETL에 강한 이유

  • driver가 전체 작업 계획을 만들고 stage로 나눔
  • shuffle, spill, retry, lineage가 배치 처리에 맞음
  • 중간 결과를 오래 들고 있는 복잡한 변환에 유리
  • 쓰기 작업과 대규모 재처리에 적합
  • DataFrame과 SQL을 같이 쓰면서 로직을 크게 만들기 좋음

Trino가 SQL 조회에 강한 이유

  • coordinator가 쿼리 계획을 만들고 worker에 나눔
  • operator들이 파이프라인 방식으로 데이터를 흘려보냄
  • connector가 읽기, 필터, projection을 아래로 밀어내는 pushdown을 수행
  • 데이터 이동을 최소화하면 빠르게 응답 가능
  • 여러 소스에 동시에 붙는 federated query에 적합

왜 ETL에 Trino만 쓰지 않는가

  • ETL은 보통 변환 단계가 많고 shuffle이 큼
  • Trino는 조회 엔진이라 긴 배치 파이프라인 제어가 Spark보다 약함
  • 대량 write, 재시도, 중간 상태 관리, checkpoint 같은 배치 안정성은 Spark가 더 맞음
  • 단순 조회나 필터, 집계는 Trino가 빠를 수 있지만, ETL 전체를 대체하는 건 아님

한 줄로 정리

  • Spark는 많이 바꾸고 많이 쓰는 일에 강하고, Trino는 있는 데이터를 빨리 조회하는 데 강함

3. Iceberg와 Parquet 차이, Iceberg가 쓰이는 이유

Parquet와 Iceberg는 다름

  • Parquet는 파일 포맷
  • Iceberg는 테이블 포맷
  • Iceberg 테이블 안의 실제 데이터 파일이 Parquet일 수 있음

Iceberg가 범용적으로 쓰이는 이유

  • schema evolution 지원
  • partition evolution 지원
  • snapshot 기반 일관성 제공
  • time travel 가능
  • hidden partitioning 지원
  • update, delete, merge 같은 테이블 동작을 지원
  • Spark, Trino, Flink 등 여러 엔진이 같이 접근하기 좋음

Iceberg 메타데이터

  • data file 목록
  • manifest 목록
  • partition 정보
  • snapshot 정보

자주 쓰는 메타데이터 테이블

  • $files
  • $manifests
  • $partitions
  • $snapshots

4. Compaction이 무엇이고 언제 해야 하는가

compaction 정의

  • 작은 파일이 너무 많이 생긴 것을 큰 파일로 합치는 작업

왜 필요한가

  • 파일이 너무 잘게 쪼개지면 open 비용이 늘어남
  • 계획 단계에서 읽어야 할 파일 수가 많아짐
  • manifest와 metadata가 커짐
  • 스캔 split과 task 수가 늘어남
  • 쿼리 지연 시간이 길어질 수 있음

속도 저하는 어떻게 감지하나

  • 같은 쿼리의 실행 시간이 예전보다 길어짐
  • P95, P99 같은 느린 구간이 커짐
  • bytes는 비슷한데 files 수만 늘어남
  • 특정 partition에서 작은 파일이 계속 쌓임
  • $files 조회 시 작은 파일 비율이 높음

작은 파일 비율은 어떻게 보나

  • 고정된 정답 퍼센트는 없음
  • 보통 목표 파일 크기를 먼저 정함
  • 흔한 목표는 128MB에서 1GB 사이
  • partition별 파일 크기 분포를 본다
  • 파일의 상당수가 목표 크기의 1/4 이하이면 경고 신호로 본다
  • median file size가 계속 작고 쿼리도 느려지면 compaction 대상

컴팩션 주기는 무엇으로 정하나

  • 파일 크기 분포
  • partition별 small file 개수
  • snapshot과 manifest 증가 속도
  • 실제 쿼리 지연 시간
  • ingest 빈도와 배치 주기

결론

  • 비율 하나로 자르지 않고, 파일 크기 분포와 쿼리 지연을 같이 봐야 함

Iceberg에서 확인하는 예

SELECT *
FROM iceberg.<schema>.<table>$files;

5. ClickHouse가 빠른 이유

구조적 이유

  • columnar storage
  • 강한 compression
  • vectorized execution
  • 필요한 컬럼만 읽음
  • primary key 기반 data skipping
  • sparse index와 mark structure로 빠르게 건너뜀

왜 OLAP에 강한가

  • 집계와 스캔이 많을수록 유리
  • 분석용 쿼리에서 읽지 않아도 되는 블록을 많이 건너뛸 수 있음
  • 대량 읽기와 집계에 최적화되어 있음

주의점

  • OLTP용 일반 RDB와 목표가 다름
  • 업데이트 중심 업무보다 분석 중심 업무에 맞음

6. Kafka에서 트래픽이 예상보다 크게 몰릴 때

가장 먼저 보는 것

  • producer가 너무 빠른지
  • consumer가 병렬로 충분히 읽고 있는지
  • partition 수가 충분한지

가장 간단한 조절

  • 처리량을 늘릴 때는 partition과 consumer를 늘림
  • 유입을 줄일 때는 producer rate limit 또는 quota를 건다

왜 partition이 중요한가

  • Kafka 병렬성의 기본 단위가 partition
  • partition이 적으면 consumer를 많이 붙여도 병렬도가 안 늘어남
  • partition이 많아야 처리량을 수평 확장하기 쉬움

실무 대응

  • partition 확장
  • consumer scaling
  • producer throttling
  • backlog 허용량 조절
  • 필요하면 buffer zone을 두고 downstream 보호

7. ETL에 예상보다 많은 데이터가 들어왔을 때

즉시 대응

  • raw zone에 먼저 안전하게 쌓음
  • consumer 또는 worker 수평 확장
  • batch size 조정
  • shuffle 설정과 memory 설정 점검
  • backpressure 적용
  • ingest rate 제한

구조적 대응

  • 수집 단계와 처리 단계를 분리
  • 재처리 가능하게 설계
  • idempotent하게 작성
  • checkpoint와 replay 경로 확보
  • 실패한 데이터는 별도 보관

핵심

  • 데이터를 잃지 않기
  • 중복이 생겨도 다시 돌릴 수 있게 만들기
  • 처리 속도와 유입 속도를 분리하기

8. 한 줄 정리

  • Parquet는 파일 포맷
  • Iceberg는 테이블 포맷
  • Spark는 대량 변환 엔진
  • Trino는 대화형 SQL 엔진
  • ClickHouse는 OLAP용 분석 DB
  • Kafka는 스트림 버퍼와 전달 계층
