소개Personal Narrative

틀린 데이터가 조회되지 않게 막는 일Keeping wrong data out of reach

결제·정산 데이터를 다루는 온프레미스 데이터 플랫폼을 만들고 운영합니다. 일 300만 건 규모의 적재를 책임지다 보니, 자연스럽게 틀린 데이터가 조회되지 않게 막는 일에 집중하게 됐습니다. I build and run the on-prem platform that carries payment and settlement data. Owning a load of roughly 3M rows a day pulled my focus toward one thing: making sure wrong data never becomes queryable.

제가 한 일의 대부분은 새 기능이 아니라 이미 잘못 돌고 있던 것에서 시작했습니다. 건수만 세던 검증을 컬럼별 해시 대조로 바꾸고, 초록불로 보이던 태스크가 사실 매일 실패하고 있었다는 걸 드러냈고, 실패가 실패로 보이게 만든 다음에야 진짜 결함들을 찾을 수 있었습니다. Most of what I have shipped began with something already running wrong. I replaced row-count checks with per-column hash comparison, exposed tasks that reported green while failing every day, and only after failures looked like failures could the real defects be found.

일 300만 건, 누적 5TB 규모를 DAG 20개로 돌리고 있습니다. 민감도가 높은 금융 데이터라, 장애가 났을 때 어디를 봐야 하는지를 정리해 두는 쪽에 시간을 많이 씁니다. Right now that is about 3M rows a day and 5 TB accumulated, across 20 DAGs. It is sensitive financial data, so a lot of my time goes into making it obvious where to look when something breaks.

Project 01 · CI/CD

망 분리 CI/CD, 산출물 없이 코드만 승격Air-Gapped CI/CD, Promote Code, Never Artifacts

기간Period 2026.07 ~ - 현재Present 역할Role 산출물을 옮기는 대신 동일성을 증명하는 구조 설계Designing a structure that proves equality instead of moving the artifact
  • 문제Problem연구개발망과 전산센터망은 통신이 불가하고 빌드 산출물을 직접 전달할 수 없어 코드만 승격 가능한 환경이었습니다. SVN과 셸 스크립트로 배포하던 구조라 개발에서 운영으로 옮길 때 변경된 파일을 손으로 골라 복사해야 했고, 그 과정에서 변경분이 자주 누락됐습니다. 무엇보다 운영에서 다시 빌드한 산출물이 개발에서 검증한 것과 같은지 보장할 방법이 없었습니다.The R&D and data-center networks cannot talk to each other and artifacts cannot be handed across, so only code may be promoted. Deploys ran on SVN and shell scripts, which meant picking changed files by hand on the way to production, and changes were regularly missed. Above all, there was no way to guarantee the production rebuild matched what had been verified in development.
  • 접근Approach산출물을 옮기는 대신 동일성을 증명하기로 했습니다. Gradle을 재현 가능 빌드로 전환해 빌드 시각과 호스트명을 산출물에서 제외하고, 개발망 빌드의 sha256을 승격 태그 메시지에 기록해 운영망 재빌드 해시와 대조합니다. 워크플로는 빌드 · 검증 · 코드 승격 · 재빌드 · 배치 5단계로 나누고, 승격 대상 트리에 jar·war·zip이 섞이면 중단하는 가드를 넣었습니다. 배포 경로에 필요한 Nexus 저장소와 SeaweedFS 오브젝트 스토리지도 함께 구축하고 권한을 설정했습니다.Rather than moving the artifact, prove the two are identical. Gradle was converted to a reproducible build so build time and hostname stay out of the output, and the dev-network sha256 is recorded in the promotion tag to compare against the production rebuild. The workflow splits into five stages, build, verify, promote code, rebuild, deploy, with a guard that aborts if the promoted tree contains a jar, war or zip. I also built the Nexus repository and SeaweedFS object storage the deployment path relies on, and set up permissions.
  • 결과Result3단계까지 완주해 운영 저장소에 코드와 태그가 반영됐고 4단계 빌드까지 통과했습니다. 설계 과정에서 초기안의 자동 해시 대조 게이트와 거기서 파생된 복잡도(자동 태그 생성, 잡 분리, 우회 변수)를 전부 걷어냈습니다. 메인테이너가 태그를 다는 행위 자체가 이미 승인 신호였고, 복잡도가 전부 그 게이트 하나에서 나오고 있었기 때문입니다.Stage 3 ran through to land code and tags in the production repository, with stage 4 building successfully. Along the way I dropped the original automatic hash-comparison gate and everything it dragged along, auto tag creation, a separate job, override variables. A maintainer applying a tag was already the approval signal, and all that complexity was coming from that one gate.

  • 문제ProblemHive 마트는 스냅샷과 트랜잭션이 없어 파티션이 없으면 행 단위 삭제조차 되지 않았고, managed/external 구분이 계속 관리 부담으로 남았습니다. 적재 검증은 원천 건수를 대상 건수 칸에 복사만 해 형태만 검증이고 실제로 비교하는 값이 없었으며, main에 바로 쓰고 확인하는 구조라 잘못 적재돼도 이미 조회가 가능했습니다.The Hive mart had no snapshots and no real transactions, so an unpartitioned table could not even be deleted from row by row, and the managed/external split stayed a maintenance cost.   • 접근Approach마트를 Trino 위 Iceberg로 전환해 스냅샷, 행 단위 수정, 시점 복구를 확보했습니다. 검증은 건수 비교를 넘어 값 지문 대조로 올렸습니다. 공통 컬럼을 대상 스키마 타입으로 캐스팅하고 공백·NULL을 정규화한 뒤 컬럼별 xxhash64 합계를 원천과 대조하며, 중복 판정은 full-row hash로 합니다. 검증 비용은 3티어로 나눠 count 티어는 적재 시 기록한 건수를 소비해 Oracle 재조회를 없애고, 대상 건수는 Iceberg $partitions 메타에서 읽어 데이터 스캔을 제거했습니다. 그리고 Nessie 브랜치에 먼저 쓰고 audit을 통과한 것만 main에 병합하는 WAP로 전환했습니다.The mart moved to Iceberg on Trino for snapshots, row-level updates and point-in-time recovery. Validation went beyond counting: common columns are cast to the target schema type, whitespace and NULLs normalised, then per-column xxhash64 sums are matched against the source, with duplicates judged by full-row hash. Cost is tiered, the count tier consumes the row count recorded at load time so Oracle is never re-read, and target counts come from Iceberg $partitions metadata instead of a data scan. Writes then stage on a Nessie branch under Write-Audit-Publish, and only what passes the audit is merged into main.
  • 결과Result검증에 실패한 데이터가 main에 노출되지 않고, 실패는 태스크 실패로 승격되어 알림이 나갑니다. 결과 확인도 서버 SSH에서 대시보드로 옮겼습니다. 추측 PK 기반 중복 오탐도 해소했는데, 원천에 ‘7’과 뒤 공백이 붙은 값이 별도 행으로 존재해 ETL trim 이후 충돌하던 것을 full-row hash로 교체해 잡았습니다.Data that fails validation never reaches main, and a failed check is promoted to a task failure with an alert. 준실시간 30분 배치, 자원 격리와 Spark 튜닝Near-Real-Time 30-Minute Batch, Isolation & Spark Tuning

  • 문제Problem일 1회 배치로는 실시간에 가까운 데이터 수요를 감당할 수 없었습니다. 주기를 30분으로 바꾸자 태스크 수가 크게 늘면서 DAG 간 자원 경합으로 병목이 생겼습니다.A once-a-day batch could not meet demand for near-real-time data. Moving to a 30-minute cycle multiplied the task count until DAGs began contending for resources.
  • 접근Approach30분 단위 준실시간 배치 파이프라인을 Airflow로 개발하고, YARN queue를 분할해 DAG별로 자원을 격리했습니다. Spark 로그에서 stage·task 편차를 읽어 불필요한 셔플과 데이터 SKEW 여부를 판별하고, 실제로 자주 실행되는 쿼리 패턴을 기준으로 파티셔닝 키를 결정했습니다. Spark 리소스 설정을 바꿔가며 실행 시간과 자원 사용량을 수십 회 측정·비교했습니다.I built the 30-minute near-real-time pipeline on Airflow and split YARN queues so resources are isolated per DAG. Reading stage and task variance in Spark logs identified needless shuffles and data skew, partition keys were chosen from the query patterns that actually run, and Spark resource settings were changed and measured against runtime and usage across dozens of iterations.
  • 결과Result30분 주기 준실시간 적재를 병목 없이 운영했습니다. 자원 격리 덕분에 한 파이프라인의 지연이 다른 파이프라인으로 번지지 않아 장애 전파 범위가 DAG 단위로 한정되고 대응 시간도 짧아졌습니다.The 30-minute near-real-time load ran without a bottleneck. Because resources are isolated, one pipeline's delay no longer pushes the others, the blast radius of a failure stays inside a single DAG and response time dropped with it.
