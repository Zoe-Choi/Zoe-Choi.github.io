담당 업무Responsibilities

결제·정산 데이터를 다루는 온프레미스 데이터 플랫폼을 만들고 운영하고 있습니다. 하루 300만 건을 적재하다 보니, 적재 결과를 검증하고 잘못된 데이터가 조회되지 않게 막는 일에 가장 신경을 씁니다. I build and run the on-prem data platform for payment and settlement data. Loading about 3M rows a day, what I care about most is validating each load and keeping bad data from becoming queryable.

건수만 비교하던 검증을 행 단위 해시 대조로 바꿨고, 성공으로 표시되던 Iceberg 유지보수 태스크가 사실은 매일 실패하고 있던 것을 찾아 실패로 드러나게 고쳤습니다. 그 뒤에 숨어 있던 결함 3건도 함께 수정했습니다. I replaced row-count checks with row-level hash comparison, and found that Iceberg maintenance tasks marked green were actually failing every day, so I made them fail visibly. Three defects hiding behind that were fixed along the way.

지금은 일 300만 건, 누적 5TB 규모를 DAG 20개로 운영하고 있습니다. 금융 데이터라서 장애가 났을 때 어디를 먼저 봐야 하는지 정리해 두는 데 시간을 많이 씁니다. Today that is about 3M rows a day and 5 TB accumulated, across 20 DAGs. Since it is financial data, I spend a lot of time writing down where to look first when something breaks.

적재 검증: 행 단위 해시 대조와 WAP 브랜치 격리Load validation: row-level hash comparison and WAP branch isolation

  • 문제Problem
    • 검증 공백 검증기가 원천 건수를 대상 건수 칸에 복사만 해 실제로 비교하는 값이 없었음No real check The validator copied the source count into the target-count field, no value actually compared
    • 즉시 노출 main에 바로 쓰는 구조라 잘못 적재돼도 이미 조회 가능Instant exposure Writes went straight to main, so a bad load was already queryable
    • 파싱·정밀도 개행·특수문자가 Hive 파싱을 깨고, 신규 컬럼의 소수점 스펙이 공유되지 않아 값이 잘린 채 적재Parsing and precision Line breaks shifted Hive columns, and an unshared decimal spec truncated values
  • 접근Approach
    • 행별 해시 전수 대조 건수 검증 뒤 모든 행의 full-row hash를 원천과 대조, 불일치가 나오면 컬럼별 해시 합계 비교로 틀린 컬럼을 좁힘Row hashes first After the count check every row's full-row hash is matched against the source; on a mismatch per-column hash sums narrow down the wrong column
    • 0건 판별 적재 결과가 0건이면 통과시키지 않고 적재 시 기록한 원천 건수와 대조해 실제 0건인지 파이프라인 오류인지 판별Zero-row check A zero-row load is checked against the source count recorded at load time to tell a real zero from a pipeline fault
    • WAP Nessie 브랜치에 먼저 쓰고 검증을 통과한 것만 main에 병합WAP Writes stage on a Nessie branch and merge to main only on pass
    • 적재 전 검사 이스케이프 처리와 원천 타입·정밀도 검사 추가Pre-load checks Escaping before load plus a source type and precision check
  • 결과Result
    • main 미노출 검증 실패 데이터는 main에 닿지 않고 태스크 실패로 승격되어 알림 발송Never reaches main Failed data is promoted to a task failure with an alert
    • 스펙 변경 감지 원천 스펙 변경이 값 손실 대신 적재 실패로 노출Spec drift surfaces A source spec change now fails the load instead of truncating values

YARN 메모리 설정 교정과 CPU 병목 해소YARN memory correction and CPU bottleneck

  • 문제Problem
    • 속도 그대로 워커 노드에 물리 메모리 256GB를 증설했지만 배치 속도는 그대로No speed-up 256GB of physical RAM was added to the worker nodes, but batch speed did not move
    • YARN 미반영 증설분이 YARN에 전혀 반영되지 않고 있었음Invisible to YARN The new capacity was not visible to YARN at all
  • 접근Approach
    • 실측 5개 노드 전체의 실제 힙 설정, YARN 용량, 앱별 실사용량을 측정 스크립트로 확인Measured Actual heap settings, YARN capacity and per-app usage across all five nodes, by script instead of guesswork
    • 낡은 설정 교정 YARN이 물리 메모리의 19%(48GB)만 보던 설정을 찾아 무중단 rolling restart로 3.3배(160GB) 확장Stale setting fixed YARN saw only 19% (48GB) of physical RAM; raised 3.3x (160GB) with a zero-downtime rolling restart
    • CPU 병목 추적 재측정에서 병목이 CPU로 이동한 것을 vCore 사용률로 확인, 고정 30-executor 프로파일이 코어를 과요청Bottleneck moved to CPU vCore utilisation showed a fixed 30-executor profile overbooking cores
    • dynamic allocation 앱마다 실사용량이 최대 250배 차이 나는 것을 근거로 고정값 대신 Spark dynamic allocation으로 전환Dynamic allocation Per-app usage varied up to 250x, so fixed executor counts gave way to Spark dynamic allocation
  • 결과Result
    • 최대 3.2배 단축 배치 처리 시간 928초 → 294초, dynamic allocation으로 작업별 자원 배분Up to 3.2x faster Batch runtime 928s to 294s with per-job allocation
    • 부수 효과 Iceberg 유지보수 654초 → 212초, Hive on Tez 실패 2건 → 0건Side effects Iceberg maintenance 654s to 212s, Hive-on-Tez failures 2 to 0
    • 무중단 전 과정 무중단, 롤백은 변수 하나만 되돌리면 됨Zero downtime Shipped without a stop, rollback is a single variable

Duplicates are judged by full-row hash too
    • 스캔 없는 건수 검증 적재 시 기록한 건수를 소비해 Oracle 재조회를 없애고, 대상 건수는 Iceberg $partitions 메타에서 읽음Counts without a scan The count check consumes the row count recorded at load time, and target counts come from Iceberg $partitions metadata
